# Agent Note：启动批次的响应体按服务字节数设上限

Status: implemented

[English](2026-09-18-combo-body-size-limit.md) | 中文

## 问题

一个 combo 批次就是一个 `<script>`，里面用 `;` 把多个插件 factory 拼在一起。这让它成为全有或全无的：第一处不完整的语句会让同一文件里后续所有 `__ModuleLoader__.load` 都不执行，而浏览器仍会触发 `load` —— 未捕获的异常不会让脚本加载失败。模块系统随后只能报出它唯一掌握的、信息量最小的事实：某个 row 没有注册；真正的错误留在 console 里。

批次切分原先只约束请求 URL（3 KiB），从不约束所服务的响应体。于是某个部署把全部 application row 作为一个 12.6 MB 的脚本提供。一个浏览器扩展拦截该脚本、重新取回、再用 `eval` 回放，在 99.11% 处把内容截断，整个页面启动失败，而报错信息指向了错误的子系统。对那个实际部署做二分测量的结果是：体积在约 1 MiB 及以下的批次都能完整到达。

## 决策

**批次同时按所服务的字节数与 URL 长度设上限。** `MAX_COMBO_BODY_BYTES` 为 1 MiB。两条上限在是否让步上不同：无法寻址的 URL 会让组合失败，而单个大于体积上限的 bundle 仍然可寻址，它会自成一批而不是失败。图顺序保持不变，因此批次边界不会把被请求的模块排到它的消费者之后。

上限度量的是批次将要服务的构建产物字节，不含 combo 框架代码与 gzip。这会略微少算框架开销，而这是有意的：它防守的阈值来自实测，一个已经接近 1 MiB 的批次无论框架开销往哪边取整，都离失败区间很远。

## 考虑过的替代方案

**不设上限，靠 `Content-Length` 检测截断。** 对观察到的失败无效。那个扩展是通过 `eval` 回放的，网络层收到的是完整响应体，截断发生在网络层之上。

**让超限的单个 bundle 也像超限 URL 那样让组合失败。** 超过体积上限的 bundle 仍然可以单独寻址、单独服务，让它失败等于为了执行一条在该情形下帮不上忙的约束而废掉一个本来可用的能力。它改为自成一批。

**改进报错信息而不改切分。** 那条误导性信息确实存在，但与本决策无关：批次执行了却没注册时，`arrive()` 仍报「loaded without registering」，真正的 `SyntaxError` 仍只出现在 console。改进这条信息已推迟，不属于本 note。

## 后果

启动发出的请求比合成一个脚本时更多。它们会并行预加载、每个都小得多，因此单次失败的代价是一个批次，而不是整个页面。

这条上限是批次体积的实际约束，不是形式条款。对本仓库构建出的 63 个 client 入口实测（近似于实际发布的 Web 名册）：总计 5.12 MiB，最大的单个入口 639 KiB，所以没有任何入口单独触到上限；而把它们全部列出的 map 形式 combo URL 是 3,359 字节。也就是说单靠 URL 上限只会把 application 阶段切成两批，第一批承载那 5.12 MiB 的绝大部分；加上体积上限后至少切成六批，没有一批超过 1 MiB。

本 note 取代了 [PDF.js 资源决策](../../archived/architecture/2026-09-12-pdfjs-assets-out-of-bundle.md) 中的资产路由那一半，该 note 已归档。`clientModules.registerAssets()` 与 `/plugins/<id>/assets/<path>` 路由都已移除：`ui-sidebar-documentpreview` 现在把 PDF.js 放在按需加载的包内 chunk 里、由该 chunk 自带二进制数据，因此这些资源根本不进入启动批次，也不再需要单独的承载路由。体积上限本身独立成立，不依赖任何单个包的体积。

## 验证

`packages/client/modules/tests/node-half.client.spec.ts` 覆盖了切分的两种结果：三个产物在所服务的响应体越过 1 MiB 之前被切开；单个超限 bundle 自成一批且不让组合失败。1 MiB 这个阈值本身来自用户对真实隧道与真实浏览器扩展做的二分测量，没有自动化测试复现那条传输链路。
